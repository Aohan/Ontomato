# Analysis Agent Tasks

- **Scope**: the dimension-orchestration form (normal or hot link) and loop-execution form of the analysis Agent, from analysis question to activities, section reports or final reply, and task review; do not treat it as a standard query chat Turn.
- **Current implementation source**: `contracts/analysis-events.ts`, `contracts/analysis-presentation.ts`, `src/services/analysis-agent/task/artifacts.ts`, `task-result.ts`, `task-read-model.ts`, `src/services/analysis-agent/dimension/`, `src/services/analysis-agent/loop/`, `src/api/routes/analysis-tasks.ts`.
- **Last verified**: 2026-09-09.

## Complete Mainline

Analysis tasks use `analysis_tasks` as the business mainline: the task entry creates the current task → organizes activities by execution form and obtains current evidence → produces section reports, charts, or the final reply for no-report tasks → closes out the run state and progress. Presentation facts are progressively written to the task row's `analysis_payload`; the page snapshot is derived at read time from that artifact. The page SSE only subscribes; it does not own the background execution.

The dimension-orchestration form proceeds as "determine plan source → collect evidence per question → charts and skills → dimension report → summary". The normal and hot links differ in only two places: **plan source** and **how current evidence is obtained**; after entering report generation and task close-out they share the same link. The dimension plan and report stages in the table below belong to this form. The loop-execution form organizes activities such as evidence collection, dispatch, and body output in chronological order, without filling a dimension plan; both forms share the same presentation contract.

Presentation events come in only four families: `analysis_run_state` delivers the full run state and server-side progress; `analysis_activity` upserts a whole activity by `activityId`; `analysis_section` sends `append` / `replace` by `sectionId`, carrying `offset` and `revision`; `analysis_charts` delivers charts and diagnostics by `scopeId`. The query layer's `thinking_state` locates a question's execution facts by `activityId + questionId`, and does not represent the loop Agent's internal reasoning chain.

The same analysis flow also carries the run protocol `run_started`, `title`, `workflow_complete`, `auth_failed`, `error`, the task lifecycle `task_completed`, `task_failed`, `task_cancelled`, the follow-up body `follow_up_chunk`, and `run_cancelled`, `run_not_found`. These events each have their own role; the last low-level event must not be treated as the global phase or progress.

## Handoff and Normal Invariants

- The seven top-level fields of `analysis_payload` are `executionMode`, `runState`, `activities`, `sections`, `charts`, `chartDiagnostics`, `finalAnswer` (optional). `runState` provides `status`, `revision`, `progress: { done, total?, label }` and optional error; the frontend only reads the server-delivered value, and does not compute task progress from phase names, event order, or artifact counts.
- Activity kinds are `plan`, `evidence`, `skill`, `narrative`, `chapter`, `publish`, `chart`, `dispatch`, `probe`, `external_tool`. Activities are located by `activityId`, ordered by `seq`, identified for update by `revision`, with status `running` / `completed` / `failed` / `cancelled`, keeping start/end times and errors; optional `groupId` expresses dimension attribution. Evidence activities carry `questionId`, status and `execution` query facts per question; a question can also be `pending`.
- Sections are located by `sectionId`, ordered by `order`, carrying optional title, heading level, body and `revision`; drafts have no terminal state, and after completion are `success` / `failed`. Charts and diagnostics attach to a section or the whole report by `scopeId`, and carry no dimension-specific attributes. The deliverable body assembles non-empty, non-failed sections in order and reuses existing charts; when there is no report artifact, it presents the activity list and `finalAnswer`.
- Dimensions, activities, sections, and query questions are handed off by stable ID; names, question wording, and ordering positions are for display only. Query results can only supplement a plan, and cannot reverse-delete failed questions, empty results, or questions with no execution plan yet. The dimension tree and four-phase cards are views of activities grouped by dimension; the loop trajectory is a chronological view of the same activity list.
- Dimension-form server progress uses `total = 100`: before the plan completes `done = 0`, after completion it is computed as `12 + round(58 × question settlement rate) + round(27 × dimension section terminal rate)`, with zero-denominator terms taken as zero. The question settlement rate is the number of questions in the activity no longer `pending` / `running` over all questions; the dimension section terminal rate is the share of planned dimensions that already have a success or failed section. Both success and failure count; after entering the run terminal state it is 100, and `done` always keeps the historical maximum; streaming report appends do not count as section completion.
- The dimension progress `label` is localized by the server per global preconditions: before plan completion it is "Generating framework"; when the evidence activity or plan questions are not settled it is "Collecting metrics"; when grouped skill/chart activities are not settled, or there are no sections and writing activities yet, it is "Data analysis"; afterwards it is "Generating report". The loop form provides no `total`; `done` is the count of settled activities (including success, failure, cancel) and only increases; `label` takes the last running activity's narrative, topic, chapter name, in-progress question, or first skill ID, otherwise the localized activity kind, and is empty when there is no running activity.
- A question-level failure in the dimension form does not erase the successful evidence of the same dimension. The task may complete with partial failure when at least one question succeeds and at least one non-empty dimension report succeeds; the task fails when all questions fail or there is no deliverable report. The loop form allows a no-report task to complete with a final reply; its terminal state cannot be judged by the number of dimension reports. Cancellation and failure are normalized by the server into still-unfinished activities, questions, and skills, preserving completed facts and body; failure to persist the final artifact cannot be wrapped as a successful completion.
- The dimension call of `deep-analysis-Report` only consumes that dimension's current evidence; the summary call only consumes successful dimension reports and summary-level supplementary artifacts. Historical hot-card body text never enters this round's writing evidence.
- The normal link reuses the basic query ABC's evidence-collection capability, but does not own the standard query's TaskPlanner, dialogue clarification, four-branch race, or page response; report generation does not consume or wait for quality checks, and review backfills late quality checks from the query layer. The hot link only reuses the saved plan, and must still re-query the current data.

## Task-Level Evidence Map

- Business facts are read from `analysis_tasks.analysis_payload`, run events, and associated `query_runs`; the task row's `request_seq` and `threadId` identify this run, and `taskId` is the business backlink, not the observable workspace root. `analysis_task_events` only keeps the internal audit of loop-form dispatched sub-Agents; activities, body and progress are all in the task artifacts.
- Recovery is based on the server snapshot of `/analysis-tasks/:id/messages`; running and terminal states are both derived from the same artifact into `snapshot.deepAnalysis`. The terminal snapshot is always adopted in whole; non-terminal states only keep the local streaming tail when the local `runState.revision` updates. After receiving a task completed, failed, or cancelled event, also take the full snapshot from this entry, clear the streaming cache and close the subscription on terminal state; do not infer task state from standard query thread messages or old running caches.
- Provenance = activity list + per-question query facts. `buildTaskProvenance` takes activities from `analysis_payload.activities`, joins `query_runs` by task `threadId + requestSeq`, `sourceKind = analysis_sub_question`, `sourceRef = questionId`, backfills each question's `execution` data, DSL, row count, error, thinking process and late quality check, then returns via `/messages`. When run identity or query records are missing, keep existing activities and questions; do not guess associations by wording or order, and do not re-execute queries.
- The observable workspace is `data/traces/{parentTurnKey}/`, isomorphic to the standard query Turn workspace: `manifest.json`, `response.md` (this task's report), task-level `raw-logs/`, `prompts/`, and `diagnostics/` (including `summary.md`, `errors.log`, and the sub-Turn index `diagnostics/index.md`). The analysis agent itself does not access the query backend, so the root layer has no backend run logs, backend structured evidence, or logic evidence; this is an evidence gap, not a build failure.
- Each query question's basic query evidence is located at `sub-Turn/{acceptance number_stable identity}/`, following the same build path and producing the same artifact set as a standard query Turn; a sub-Turn's `response.md` is that query question's own reply and is not rolled back into the displayed task report. The root index lists all sub-Turns flat, with question execution status and diagnostic artifact status in separate columns, not sectioned by dimension or trajectory.
- Retesting should recreate the same question's task, check the execution form, the plan and question-level evidence in the activities, the current data time, sections or final reply, server progress and task terminal state, and compare real-time events with the `/messages` snapshot; the hot link cannot substitute historical hot-card content for this round's replay evidence.
