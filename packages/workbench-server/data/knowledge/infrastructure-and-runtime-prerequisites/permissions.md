# Permissions

- **Scope**: the external authorization that ontomato pages and proxied requests depend on, and the row/column data permissions in the query backend query execution; does not save the current permissions of users, roles, or positions.
- **Current implementation source**: `src/api/routes/backend-proxy.ts`; the query backend `util/HttpRequestUtil.java` (`addVectorAndRowPermission`), `util/DslPermissionUtil.java`, `service/sys/bean/permission/UserDataPermission.java`, `service/impl/ABCProgramServiceImpl.java`.
- **Last verified**: 2026-08-26.

## Role and Dependencies

- ontomato only proxies and displays the facts of the external permission system, and does not maintain permission entities locally. Page, menu, or API failures must be distinguished from login state, proxy errors, and service errors.
- The session `tk` is the login state used by existing the query backend tool calls. Permission facts still belong to the external system and cannot be inferred from prompts or static knowledge.
- Data permissions are matched exactly by class name (`UserDataPermission`'s fieldPermissions / rowPermissions are looked up by className `equals`, with no prefix or alias tolerance); runtime temporary class names therefore naturally find no permission configuration.

## Where Data Permissions Take Effect in the Execution Chain

- **Row permissions** are injected after DSL validation and **before** data adapter routing (`HttpRequestUtil.addVectorAndRowPermission`): first perform vector condition rewriting, then look up row-permission rule by the class name of each object in `steps[0]`, and on hit wrap it into the object's original condition with `and`. Both database mode and relational mode must pass this step.
- After injecting row permissions, the same query forms **two copies of the DSL, each executed once** (no-permission version + row-permission version); with `onlySearchPermissionData`, only the row-permission version executes.
- **Column permission masking** happens after results return, replacing the values of unauthorized columns with `****`. The system has **three mutually independent masking implementations**: DSL direct-query results (`DslPermissionUtil.dealDslAnswerWithPermission`), traditional ABC post-calculation results (`dealAfterCalculateAnswerWithPermission`), and ABC program/Harness Python results (`ABCProgramServiceImpl.dealPythonReturn`). The three only share the same placeholder string; their judgment logic differs (the direct-query path exempts derived columns and grouping columns; the post-calculation path's grouping exemption only takes effect when FieldPermission exists on the class).

## On-Site Evidence

- **The whole process of row and column permissions taking effect is silent, with no dedicated logs.** "Whether `****` is in the logs" does not constitute evidence. Indirect observation points: when row permissions are injected, the INFO-level DSL/SQL log text adds an extra `{"operator":"logic","and":[original condition, permission condition]}` wrapper to the object condition, and the same sessionId shows two queries.
- `****` appearing in results cannot be directly attributed to real permissions: at least three mechanisms produce it, and the phrase "data permission restriction" in conclusion text is an explanation generated by the diagnosis system itself, to be treated only as a hypothesis to falsify. For the triage method, see [Mechanism triage for masked placeholders appearing in results](desensitized-placeholder-mechanism-triage.md).
- There is currently no independent permission-read tool, nor can user, role, or position permissions be listed directly. Use the current page/API state, returned errors, result differences of the same query under different known identities, and authorization information the user provides from the external permission system.
- When existing capabilities cannot obtain external authorization details, clearly state "permission facts pending supplement" and list the needed user identity, resource, action, and external authorization evidence.

## Deviation Propagation and Verification

- Page/API authorization deviation usually appears at the entry or proxy stage; data permission deviation changes visible rows and columns at the data-fetch and result-masking stages, and continues to affect conclusions, charts, and reports.
- Real column permissions are determined by static FieldPermission configuration and behave consistently for the same user across questions; `****` that drifts across sessions or questions is more likely from other mechanisms.
- Authorization changes must be made by an authorized user in the fact system. After the change, retest with the same identity, the same action, or the same query, and confirm only the expected scope is restored, without expanding to data that should not be visible.
