# ABC Harness Mode

- **Scope**: when the basic query `abc` branch uses `harness` mode; not applicable to the traditional question analyst → DSL generator pipeline.
- **Current implementation source**: backend `ABC_PROGRAMMER` tool loop, and `src/services/data-query/branches/abc-harness-branch.ts`, `adapter.ts`.
- **Last verified**: 2026-08-26.

## Single-Agent Tool Closed Loop

The ABC Programmer Agent first determines sub-questions, then loops around each sub-question: explore schema, business knowledge and real data → write Python with inline DSL calls → run it with `test` → modify based on results or errors → test again → formally output with `outputCode`. It is not a serial chain of three fixed Agents ("question analyst, DSL generator, post-calculator").

`test` only verifies and temporarily stores the current code and test results under `subQuestionNo`, not a formal output; `outputCode` reads the same number's last-tested code and, together with the question and field sources, forms the formal `DATA_TYPE` data event. As many sub-questions as the Agent declares, so many `outputCode` calls should be completed, one formal code artifact per sub-question. The `test` print result is only a precheck: as long as the output fields involve row permissions, `outputCode` re-executes the code under the current user's permissions, so the final data must be based on the formal data event / query run.

## Formal Artifacts and Permission Boundaries

- The downstream formal data event simultaneously saves `question`, `data`, non-empty `code`, and `outKeyRefs`. The code describes the formal query and computation logic; `outKeyRefs` describes which class/property each output field comes from, and whether it is grouped or aggregated; the event's `data` is this round's final data fact.
- Python's inline DSL calls share the [query execution foundation](index.md) with other query entries (vector rewriting, row permission injection, adapter routing); DSL referencing runtime temporary tables will hit the [unregistered class name failure](unregistered-class-name-causes-npe-or-invalid-sql.md).
- DSL calls in Python are still constrained by the current user identity and data permissions. When relevant row permissions exist, `outputCode` re-executes the code under the current user's permissions, and results may differ from the earlier `test` print; permission masking is a result fact, and the Programmer, field adapter, or answer organizer cannot guess hidden values, nor bypass permissions by switching to different code.
- `data=[]` with non-empty `code` is a valid zero-row query artifact; a single data event with empty code is a protocol error, and must be discarded, but does not roll back other code-complete events in the same response.
- The branch completes the answer contract when the Harness stream ends normally, at least one code-complete data result is formed, and the dedicated answer organizer or its fallback completes. Session/node localization, process messages, or successful tests alone cannot independently constitute a race winner.
- When legal data events already exist during execution, an atomic recoverable query artifact snapshot is published; on later failure it can only be returned along with the overall error when the basic query has no winner, and cannot impersonate a complete Harness answer.

## Key On-Site Artifacts

- `prompts/2.1 ABCHarness Programmer-*.md` contains the full tool loop. For each `subQuestionNo`, the last successful `test` code is used to explain the subsequently `outputCode`-formalized program; test prints only prove the precheck, and final data must match the formal `DATA_TYPE` / query run, not substitute test prints.
- Field display and answer organization are left in `3.3-field-display-planner-*` and `3.19-deep-thinking-answer-polisher-*` respectively; they consume formal artifacts and do not re-decide Python.
- `query_runs` / query snapshots save the Dataset, `abcCodes`, `abcOutKeyRefs`, and winner status; `response.md` only saves the final page presentation.
