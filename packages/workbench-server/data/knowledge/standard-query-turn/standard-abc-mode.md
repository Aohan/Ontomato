# Standard ABC Mode

- **Scope**: when the basic query `abc` branch uses the traditional `no_tool_fixed` or `tool_fixed` mode; not applicable to ABC Harness.
- **Current implementation source**: backend ABC's `QUESTION_SPLITER*`, `DSL_COOKER`, `TOOL_AND_PYTHON_CALCULATOR` run artifacts, and `src/services/data-query/abc-tool.ts`, `client.ts`, `adapter.ts`, `conclusion.ts`.
- **Last verified**: 2026-08-26.

## Mode Mainline

Traditional ABC is multi-role solving: the question analyst forms one or more execution sub-questions and an optional `finalCalculation`, the DSL generator forms executable DSL for each sub-question, the database executes under current permissions, and when necessary the data analysis expert performs Python post-calculation based on basic results. Each result goes through unified field display planning, then traditional ABC's Conclusion completes the answer close-out.

The same role may generate, evaluate, or select candidates multiple times in one round; the prompt file numbers only indicate call order and do not automatically represent the final adopted result. Multiple execution sub-questions may also proceed in parallel; the real execution fact is the split, DSL, the database results and post-calculation that the current session finally accepts and enters into the authoritative data block, not a presumed serial chain stitched by file time.

## ABC Sub-Query Contract

An ABC sub-query completes three steps within the boundary of one connected result table: **A** select a connected object subgraph and its relations, **B** filter objects within that subgraph and extract needed fields, **C** perform in-table computation on this table such as grouping, aggregation, and sorting. Each sub-query independently produces one table; combining across multiple result tables, or operations beyond single-table ABC capability, must enter `finalCalculation` and be done by Python post-calculation, and cannot be stuffed back into some sub-query to pretend completion.

## Result Authority and Completeness

- Sub-questions can be generated and executed in parallel, but output is preserved in backend authoritative result order. Each successful execution unit forms a Dataset, including `answer=[]` zero-row results.
- Without `finalCalculation`, the sub-question results jointly support the answer; when post-calculation exists, that post-calculation's successful result is the authoritative final answer for the complete user question, even if it is zero rows. Non-empty intermediate results must not substitute for a zero-row final post-calculation.
- Direct DSL results are explained by output field descriptions for business fields; post-calculation results are also explained by the actual Python code for computed fields, scale and precision. FieldAdapter only plans; numeric conversion is executed by deterministic rules.
- The post-calculation LLM call loads the `skills/aftercalculate` skill directory each time; load failure only logs WARN and goes through the no-skill degraded branch, **without affecting post-calculation output**. Post-calculation results also go through independent lineage-based permission judgment, whose `****` form differs from real column permissions, see [Mechanism triage for masked placeholders appearing in results](../infrastructure-and-runtime-prerequisites/desensitized-placeholder-mechanism-triage.md).
- ABC completes the full answer contract and can participate in the race only when all execution sub-questions succeed and traditional Conclusion or its fallback completes. Afterwards, only the standard query scenario attaches a quality check.
- When any execution unit fails, traditional ABC cannot win; the already-formed datasets, DSL, code, lineage and errors still compose an atomic recoverable query artifact. It is only returned along with the overall error when the entire basic query has no complete winner, and it does not undergo quality checks.

## Key On-Site Artifacts

- `prompts/2.1 Question Analyzer-*.md`, `2.2-dsl-generator-*.md`, `2.3-data-analysis-expert-*.md` respectively record the model's actual input/output; for multiple files, judge the adoption relationship by combining session and final execution facts.
- `diagnostics/query_logic.md` saves the actual query logic, returns and `finalCalculation`; it is closer to the execution facts than model text with only candidate DSL.
- `query_runs` and query snapshots save the final Dataset, code/DSL, replay plan, winner and completeness; the page `response.md` only proves what the user saw.
